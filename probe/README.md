# Шаг 0: замер потока поисковых запросов

Проверка главной гипотезы идеи: **сколько чужих поисковых запросов видит
рядовая нода Soulseek, подключённая к distributed-сети как ребёнок.**

Ни раздачи, ни скачивания, ни индекса. Только логин, подключение к
родителю и счётчик входящих `DistribSearch`.

## Запуск

    SOULSEEK_USERNAME=your_name SOULSEEK_PASSWORD=your_password bash run.sh 5m

Аргумент — длительность замера, по умолчанию `5m`. Сборка и запуск
целиком в Docker, на хост ничего не ставится.

Результат пишется в `results/searches.jsonl` — по строке JSON на каждый
пойманный запрос:

    {"time":"2026-08-09T13:22:41Z","query":"aphex twin selected ambient"}

Файл дописывается, а не перезаписывается, — несколько прогонов
складываются в один набор.

## Что делает

1. Логинится на `server.slsknet.org:2242` (`Login`, код 1).
2. Сообщает порт (`SetWaitPort`, 2), отказывается принимать детей
   (`AcceptChildren`, 100), заявляет отсутствие родителя
   (`HaveNoParent`, 71).
3. Получает `PossibleParents` (102) — до 10 кандидатов — и подключается
   ко всем сразу, отправляя `PeerInit` типа `D`.
4. Родителем считается первый, кто прислал `DistribSearch`. После этого
   сообщает серверу свою позицию: `HaveNoParent`=false, `BranchLevel`
   (126), `BranchRoot` (127).
5. Каждые 10 секунд печатает: всего запросов, запросов в секунду, топ
   слов и последние 20 запросов.

## Приватность

`DistribSearch` несёт ник искавшего. Он **читается и выбрасывается** —
ни в статистику, ни в файл он не попадает: в структуре записи поля под
него просто нет. Это не оптимизация, а решение: идея строится на спросе,
а не на слежке за людьми.

## Известные риски

- **Версия клиента.** Стоит `major = 200`, чтобы не выдавать себя за
  Nicotine+ (160) или Soulseek NS/Qt (157). Если сервер отвергнет логин
  из-за незнакомой версии — попробовать 160 / minor 3.
- **Пароль уходит на сервер открытым текстом.** Так устроен протокол.
- **Нода не слушает входящие соединения** и не принимает детей. Для
  замера это допустимо, для постоянной работы — нет.
- Кандидаты в родители могут не ответить или отказать; программа просто
  пробует всех из списка и ждёт следующий `PossibleParents`.

## Результат прогона 9 августа 2026

    7753 запроса за 166 секунд
    46.7 в секунду в среднем, пик 92
    96.9% уникальных
    позиция в дереве: уровень 5, корень ratman65

Около 4 миллионов запросов в сутки с одного рядового узла. Для чартов
спроса этого достаточно, парк нод не нужен.

## Чему научил первый запуск

- **Версия клиента решает всё.** С `major = 200` сервер отвечает на
  сообщения, но `PossibleParents` не присылает никогда. С `160.3`
  (Nicotine+) кандидаты приходят за 10 секунд. Отсюда переменные
  `CLIENT_MAJOR` / `CLIENT_MINOR` — по умолчанию 200, для рабочего
  прогона нужно 160/3.
- **`SetStatus` (28) обязателен.** Без объявления статуса «онлайн»
  сервер не обслуживает узел полноценно.
- **IP кандидата разбирается со старшего байта**, а не наоборот.
- **Родитель должен быть один.** На трёх соединениях один и тот же
  запрос приходит пятикратно и счёт завышается впятеро.

## Запуск рабочего замера

    VERBOSE=1 CLIENT_MAJOR=160 CLIENT_MINOR=3 bash run.sh 3m
