# Принятые решения

Журнал решений, которые нельзя вывести из кода. Дата — когда решение принято.

## 1. Клиентская библиотека Soulseek — `aioslsk` (2026-08-11)

**Решение:** используем [`aioslsk`](https://github.com/JurgenR/aioslsk) (asyncio, Python 3.10–3.14, GPL-3.0-or-later), версия 1.6 и выше.

**Почему:** единственный поддерживаемый клиент протокола на Python, который реально участвует в distributed-сети: подключается к parent-пирам, принимает от них поисковые запросы и передаёт их своим детям. Nicotine+ — приложение, а не библиотека; реализации на Go и Node мимо выбранного стека. Это закрывает главный риск проекта (шаг 12 дорожной карты) готовым кодом.

**Следствие:** проект становится GPL-3.0 (см. решение 2).

## 2. Лицензия — GPL-3.0 (2026-08-11)

**Решение:** весь soulseek-charts публикуется под GPL-3.0.

**Почему:** `aioslsk` под GPL-3.0-or-later, и линковка с ней распространяет условия лицензии на производную работу. Разделение на два репозитория ради более свободной лицензии для API усложнило бы поддержку без реальной выгоды для открытого проекта.

## 3. `SearchRequestReceivedEvent` не подходит для сбора (2026-08-11)

**Решение:** подписываемся на низкоуровневое `MessageReceivedEvent` и фильтруем сообщения `DistributedSearchRequest.Request` и `DistributedServerSearchRequest.Request`.

**Почему:** высокоуровневое событие `SearchRequestReceivedEvent` испускается внутри `_query_shares_and_reply` только после проверки `if len(visible) + len(locked) == 0: return`, то есть **лишь когда запрос совпал с нашими раздачами**. Для узла без раздач это ноль событий, для узла с раздачами — выборка, смещённая в сторону того, что у нас есть. И то и другое уничтожает смысл чартов.

**Как применять:** обработчик регистрируется на единственной шине клиента (`client.events`), поля берём подтверждённые по исходникам библиотеки: `username`, `ticket`, `query`. Отметки времени в сообщении нет — ставим свою в момент приёма.

```python
async def on_message_received(event: MessageReceivedEvent) -> None:
    message = event.message
    if isinstance(message, (DistributedSearchRequest.Request,
                            DistributedServerSearchRequest.Request)):
        record_search_query(username=message.username, query=message.query)
```

## 4. Узел ничего не раздаёт (2026-08-11)

**Решение:** список раздач пуст, файлы в сеть не отдаются.

**Почему:** раздача любых файлов создаёт юридический риск, несоразмерный исследовательской задаче. Вклад в сеть при этом не нулевой: узел продолжает передавать поисковые запросы своим детям в distributed-дереве, то есть выполняет работу маршрутизатора.

**Следствие:** решение 3 становится не просто предпочтительным, а единственно возможным — без раздач высокоуровневое событие не сработает никогда.

## 5. Имена пользователей — постоянный псевдоним, ограниченный сроком хранения (2026-08-12)

**Отменяет** прежнее решение от 2026-08-11 о ежедневной ротации соли.

**Решение:** `username` никогда не попадает в хранилище в читаемом виде. Пишем `HMAC-SHA256(секрет, username)`, усечённый до восьми байт. Псевдоним **постоянный**. Ограничивает профиль не ротация, а срок жизни данных:

| Слой | Что содержит | Срок |
|---|---|---|
| `search_query_events` | псевдоним + сырой текст запроса | 30 дней |
| `parsed_search_queries` | псевдоним + артист и трек | 90 дней |
| часовые агрегаты | людей нет, только счётчики | 3 года |

**Почему:** постоянство — это то, что делает возможными счёт спроса по людям на длинной дистанции и рекомендации по поведению (метод сцен). Ротация убивала обе возможности ради защиты, которую дешевле получить сроком хранения: профиль истекает, хотя псевдоним и не меняется. Чарты живут годами, потому что в них нет людей.

**Как применять:** секрет живёт в `PRIVACY_HASH_SECRET` (не короче 32 символов), в репозиторий не попадает. Это учётные данные: с ним архив сводится обратно к настоящим никам, поэтому при переносе или публикации данных ключ не должен ехать вместе с ними. Усечение до восьми байт повторяет формат прототипа — его архив при желании можно состыковать с новым хранилищем.

## 6. Прототип на Go удалён, проект переписывается на Python (2026-08-12)

**Решение:** каталоги `probe/`, `charts/`, `resolver/`, `analysis/` удалены из репозитория. Каталог `docs/` (заметки о протоколе и о передаче дел) сохранён.

**Почему:** решение владельца проекта — Go-версия считается прототипом, дальнейшая работа идёт на Python. Удалённый код остаётся в истории git (коммиты `80e7962`, `20b076e`, `b7e5a50`) и восстановим в любой момент. Заметки в `docs/` кодом не являются: это результаты экспериментов на живой сети, повторно они стоили бы дней работы.

**Побочная находка:** в прежнем `.gitignore` строка `collector` (имя собранного бинарника) поглощала одноимённый каталог, поэтому **исходники демона никогда не попадали в репозиторий** — они существуют только на машине автора. В новом `.gitignore` этого правила нет.

## 7. Измерения прототипа имеют приоритет над предположениями (2026-08-12)

**Решение:** следующие факты установлены экспериментом на живой сети и не пересматриваются без новых данных.

- **Один родитель, не несколько.** Родители ретранслируют одни и те же запросы; три родителя завышали счётчики примерно впятеро.
- **Одного узла достаточно.** Потоки от родителей на уровнях 4 и 6 идентичны (Жаккар 0.995–0.999). Глубина влияет на задержку, а не на охват.
- **Объём:** 46.7 запросов в секунду, около 4 млн в сутки, ~30 000 разных искателей в сутки, ~96% запросов уникальны.
- **Спрос считается людьми, а не запросами** — иначе чарт определяет один человек, перебирающий дискографию.
- **Ники никогда не резолвятся в адреса**, хотя сервер это позволяет. Иначе псевдонимизация теряет смысл.

**Следствия для текущего кода:** цифра 46.7 запросов в секунду заменяет догадки в лимитах контейнеров; при ~96% уникальных запросов имеет смысл перепроверить TTL и объём сырого слоя в ClickHouse.

## 8. Версия клиента — только явный выбор оператора (2026-08-12)

**Решение:** по умолчанию узел не заявляет чужой номер версии и потому **не собирает ничего**. Номер задаётся переменными `SOULSEEK_CLIENT_VERSION_MAJOR` и `SOULSEEK_CLIENT_VERSION_MINOR`; без них коллектор при старте пишет предупреждение и объясняет последствия.

**Почему:** сервер выдаёт распределённых родителей только знакомым версиям. Заявить номер чужого клиента технически просто, но это делает тот проект ответственным за поведение нашего узла. Такой шаг должен совершать человек, разворачивающий узел, осознанно и своей рукой — а не код по умолчанию.

**Что остаётся нерешённым:** законного способа зарегистрировать собственную версию пока нет. Пока его нет, проект полезен только тому, кто готов сделать этот выбор сам.

## 9. Лимиты рассчитаны под конкретную машину (2026-08-12)

**Решение:** ClickHouse — 2 ГБ и 2 ядра, коллектор — 384 МБ, API — 256 МБ. Внутренний потолок ClickHouse 1.5 ГБ, на один запрос 500 МБ.

**Почему:** стек живёт на рабочей машине автора: 8 ядер и 14 ГБ, но занято около 11 ГБ двадцатью восемью посторонними контейнерами, свободно ~3.5 ГБ. Прежние `8G` под ClickHouse на этой машине означали бы OOM у соседей или у самого сервера. При переезде на выделенный хост числа поднимаются вместе с лимитом контейнера — они специально записаны в комментарии рядом.

## Открытые вопросы

- **Законная регистрация версии клиента.** См. решение 8: способа нет, и это единственное, что отделяет проект от сбора данных.
- **Переключение с Go-сборщика.** Прототип работает на этой же машине под аккаунтом `soulseekcharts` и продолжает пополнять архив. Останавливать его следует в момент переключения, а не раньше: до появления рабочего Python-коллектора остановка означает просто паузу в сборе. Аккаунт переиспользуется после остановки.
- **Секрет псевдонимизации прототипа.** Лежит на машине автора. Если использовать тот же секрет, псевдонимы нового хранилища совпадут со старым архивом и два периода сборки можно будет свести вместе. Решение за пользователем: это учётные данные, я к ним не прикасаюсь.
