# Дорожная карта soulseek-charts

Узел Soulseek, который записывает, что ищет сеть, и инструменты для осмысления этих данных.

**Стек:** Python (asyncio) → ClickHouse → HTTP API + веб-дашборд
**Собираем:** поисковые запросы, разбор на артиста/трек, результаты и раздачи

---

## Этап 0. Фундамент репозитория

1. `.gitignore` (Python, `.claude/settings.local.json`, `.env`, данные)
2. Docker-инфраструктура: `docker-compose.yml` (collector + ClickHouse + API + web), Dockerfile'ы, всё ставится только внутри контейнеров
   - 2a. Ресурсные лимиты на каждый контейнер (CPU, память, файловые дескрипторы, размер логов) — прописаны с самого начала, а не добавляются после первого OOM
   - 2b. Внутренние лимиты ClickHouse согласованы с лимитом контейнера (`max_server_memory_usage`, `max_memory_usage`, `max_execution_time`)
   - 2c. Ограничен рост данных на диске: TTL на сырые события и том с известным потолком
3. Скрипты-обёртки в `scripts/` (запуск, тесты, линт, миграции) — никаких ad-hoc команд
4. Конфигурация через `.env` + `.env.example` (учётные данные Soulseek, адрес ClickHouse)
5. `PATTERNS_RU.md` / `PATTERNS_EN.md` — стиль и структура кода проекта
6. CI: линт (ruff) + типы (mypy) + тесты на каждый push

## Этап 1. Разведка протокола (обязательна до кода)

7. Выбрать и проверить библиотеку клиента Soulseek на Python — кандидаты `aioslsk`, наработки Nicotine+; критерий: поддержка distributed-сети, а не только собственного поиска
8. Подтвердить на живом соединении, какие сообщения реально доходят до узла и какие поля в них есть (никаких предположений о структуре — только то, что видно в трафике)
9. Прикинуть объём: сколько запросов в минуту проходит через один узел — от этого зависит схема хранения
10. Правовые и этические рамки: узел ничего не раздаёт нелегального, персональные данные пиров не пишем

## Этап 2. Узел-коллектор

11. Долгоживущий демон: логин на сервер, автопереподключение с экспоненциальной задержкой, здоровье процесса
12. Встраивание в distributed-сеть (parent/child-соединения) — без этого сквозного потока запросов не будет
13. Приём и декодирование входящих поисковых сообщений
14. Буфер в памяти и батчевая вставка в ClickHouse (по размеру и таймауту), устойчивость к недоступности базы данных
15. Метрики: запросов в секунду, потери, разрывы соединений, задержка вставки
16. Сбор результатов и раздач по выборке запросов — с ограничением частоты, чтобы не мешать сети

## Этап 3. Хранилище

17. Схема ClickHouse: сырая таблица событий (`MergeTree` по времени, партиции по дню, TTL на сырьё)
18. Отдельный слой нормализованных запросов (артист, альбом, трек)
19. Материализованные представления для агрегатов: топ по часу, дню, неделе
20. Миграции — самодостаточные снимки, имена колонок литералами; проверка «с нуля» на пустой базе
21. Решение по приватности: имя пользователя из результатов не хранить либо хешировать с солью — зафиксировать письменно

## Этап 4. Осмысление данных

22. Нормализация сырого текста: регистр, диакритика, мусор (`320kbps`, `flac`, `[2024]`, пути к файлам)
23. Парсер «артист — трек / альбом» с оценкой уверенности; неразобранное не выбрасываем, а помечаем
24. Дедупликация вариантов написания одного артиста
25. Фильтрация ботов и спам-запросов (одинаковые запросы пачками)
26. Золотой набор из ~200 размеченных вручную запросов и метрика точности парсера
27. (Опционально, позже) сверка с внешним каталогом (MusicBrainz) для канонизации имён

## Этап 5. Чарты и API

28. Определить сущность «чарта»: топ-N за период, с рангом, дельтой к прошлому периоду и признаком «новичок / возвращение»
29. HTTP API (FastAPI): топ-чарты, карточка артиста и трека, временной ряд, поиск
30. Пагинация, кэш ответов, версионирование `/api/v1`
31. Экспорт CSV и JSON для исследователей

## Этап 6. Дашборд

32. Витрина: главный чарт, график динамики, страница артиста и трека
33. Переключение периода (день, неделя, месяц) и сравнение периодов
34. Страница «о проекте»: как собираются данные, что не собирается, ограничения выборки
35. Адаптивность и тёмная тема

## Этап 7. Эксплуатация

36. Деплой одной командой, автоперезапуск демона
37. Резервные копии ClickHouse и проверка восстановления
38. Оповещения: коллектор молчит дольше N минут, вставки падают, заканчивается диск
39. Дашборд состояния самого узла (время работы, объём собранного)
   - 39a. Мониторинг упирания в лимиты: оповещение об OOM-kill контейнера и о превышении 80% лимита памяти, рост очереди вставки. Поведение под лимитом проверено заранее — при искусственно заниженной памяти коллектор деградирует (буферизует, повторяет), а не падает с потерей данных

---

## Определение готовности

- Узел живёт неделями без ручного вмешательства
- Поток запросов пишется без потерь, объём предсказуем
- Парсер разбирает не менее 80% запросов с известной точностью
- На дашборде виден недельный чарт, обновляемый автоматически
- Ни один контейнер не может утянуть хост: у всех выставлены лимиты CPU и памяти, поведение при упирании в них проверено
- Любой может воспроизвести проект: `git clone` → одна команда → работающий стек

---

## Главные риски

- **Шаг 12** — без встраивания в distributed-сеть сквозного потока запросов не будет, и проект не взлетает
- **Шаг 26** — без размеченного набора качество парсера останется ощущением, а не числом
